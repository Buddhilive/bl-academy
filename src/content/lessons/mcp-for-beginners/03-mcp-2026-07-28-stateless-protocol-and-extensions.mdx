The **MCP `2026-07-28` specification** is the biggest architectural shift since the protocol launched. Earlier revisions (`2025-11-25`) required a stateful `initialize` / `initialized` handshake and an `Mcp-Session-Id` header that pinned every client to a single server instance. That forced horizontal deployments to maintain sticky load-balancer routing and shared session stores.

MCP `2026-07-28` fixes this by making the protocol **stateless at the transport layer**, formalizing a versioned **Extensions framework**, and introducing a clear 12-month deprecation lifecycle for legacy features.

---

## Stateless Protocol Core (`2025-11-25` vs. `2026-07-28`)

In `2026-07-28`, every HTTP request is completely self-contained. Any backend replica behind a load balancer can serve any request.

| Capability | Legacy (`2025-11-25`) | Current (`2026-07-28`) |
| :--- | :--- | :--- |
| **Session Startup** | Mandatory `initialize` / `initialized` handshake | Removed (`server/discover` optional up front) |
| **Session Pinning** | `Mcp-Session-Id` header on every call | Removed; protocol layer is 100% stateless |
| **Client Metadata** | Sent once during `initialize` | Sent per request inside `params._meta` |
| **Application State** | Hidden in transport session store | Explicit domain handles (`basket_id`, `job_id`) |
| **HTTP Routing** | Inspect JSON body to route | Required `Mcp-Method` and `Mcp-Name` headers |
| **Missing Resource** | Custom `-32002` error code | Standard JSON-RPC `-32602` (Invalid Params) |

### Explicit State Handles & Multi-Round-Trip Elicitation

Removing protocol sessions does not mean your application cannot be stateful. Instead of hiding state in an `Mcp-Session-Id` header, a tool mints an explicit handle (like `basket_id: "b_123"`), and the model passes that handle back as a normal argument on subsequent `tools/call` requests.

Similarly, when a server needs user confirmation mid-call without holding an SSE stream open, it returns an `InputRequiredResult` containing `inputRequests` and an encoded `requestState` payload:

$$\text{requestState} = \text{BASE64}\left(\text{JSON}(\{\text{step}, \text{pending\_action}\})\right)$$

The client gathers the user's answer and retries the call with `inputResponses` plus the echoed `requestState`, allowing any stateless server replica to resume seamlessly.

## Routable, Cacheable, Traceable & Extensible

Three HTTP metadata additions make stateless MCP traffic easy to operate at scale:

1. **Routing Headers**: `Mcp-Method` (e.g., `tools/call`) and `Mcp-Name` (e.g., `search`) are required on Streamable HTTP requests so API gateways can route and rate-limit without parsing JSON bodies. Servers reject requests where headers and body disagree.
2. **List Caching**: `tools/list` and `resources/read` results include `ttlMs` and `cacheScope` (`"private"` or `"public"`) modeled on HTTP `Cache-Control`.
3. **W3C Trace Context**: `_meta` carries `traceparent`, `tracestate`, and `baggage` for end-to-end OpenTelemetry tracing.

### First-Class Extensions & Feature Deprecations

Extensions now use reverse-DNS IDs negotiated via an `extensions` capability map. Two official extensions ship with `2026-07-28`: **MCP Apps** (sandboxed `ui://` interactive HTML interfaces) and **Tasks** (`tasks/get`, `tasks/update`, `tasks/cancel`, removing session-bound `tasks/list`).

Meanwhile, four older features are marked **Deprecated** with at least 12 months before removal:

| Deprecated Feature | Modern `2026-07-28` Replacement |
| :--- | :--- |
| **Roots** | Explicit tool parameters, resource URIs, or server configuration |
| **Sampling** | Direct integration with LLM provider APIs (`google-genai`) |
| **Logging** | `stderr` for `stdio` transports; OpenTelemetry for structured observability |
| **Dynamic Client Registration (DCR)** | Client ID Metadata Documents (CIMD) |
