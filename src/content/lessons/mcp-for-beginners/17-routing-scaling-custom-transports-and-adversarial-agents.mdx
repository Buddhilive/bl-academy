Single-agent LLM pipelines have a well-known blind spot: they tend to agree with their own first draft and miss subtle edge cases. One of the most effective ways to catch hallucinations and stress-test technical decisions is **Adversarial Multi-Agent Reasoning**, where two agents argue opposite sides while querying the **exact same MCP tool server**, and a third Judge agent evaluates the debate.

---

## Routing, Horizontal Scaling & Custom Transports

Before scaling to multi-agent debates, distributed MCP deployments rely on three infrastructure patterns:

| Pattern | How It Works | Primary Benefit |
| :--- | :--- | :--- |
| **Header-Based Routing** | L7 proxies route `Mcp-Method` / `Mcp-Name` across specialized backend pools | Isolates heavy compute tools from fast metadata lookups |
| **Stateless Horizontal Scaling** | `2026-07-28` removes `Mcp-Session-Id`; any replica handles any call | Zero sticky-session bottlenecks under autoscaling |
| **Custom Transports** | Async Queue / WebSocket / gRPC adapters implementing JSON-RPC read/write streams | Connects air-gapped or event-driven message buses |

---

## Adversarial Multi-Agent Debate with Shared MCP Tools

In an adversarial debate, **`ForAgent`** argues in favor of a proposal and **`AgainstAgent`** argues against it. Crucially, **both agents connect to the exact same `FastMCP` tool server** (`web_search`, `run_python_sandbox`, `doc_reader`). Sharing one tool server eliminates information asymmetry, so any disagreement reflects genuine reasoning differences rather than one agent having hidden data.

After two or more rounds (`Opening Argument` -> `Rebuttal`), **`JudgeAgent`** scores both sides on **Evidence Quality**, **Logical Soundness**, and **Edge-Case Coverage** to emit a calibrated final verdict.
