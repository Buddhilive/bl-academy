## The 4-Layer MCP Database Architecture

| Layer | Component | Responsibility |
| :--- | :--- | :--- |
| **1. Protocol Layer** | `FastMCP` | Tool/resource registration, Pydantic schemas, JSON-RPC routing |
| **2. Business Logic Layer** | `SalesAnalyticsService` | Store access validation, KPI calculation, caching |
| **3. Data Access Layer** | `DatabaseProvider` | Connection pooling, query timeouts, **Row-Level Security (RLS)** context binding |
| **4. Infrastructure Layer** | Telemetry & Config | Structured logging, OpenTelemetry spans, environment secrets |

## Multi-Tenant Schema & Row-Level Security (RLS)

In a **shared-database, shared-schema** multi-tenant design, `stores`, `customers`, `products`, `sales_transactions`, `sales_transaction_items`, and `product_embeddings` all carry a `store_id` tenant column.

In production PostgreSQL + `pgvector`, you enforce isolation right inside the database engine so even a buggy query cannot leak another store's data:

```sql
ALTER TABLE retail.customers ENABLE ROW LEVEL SECURITY;

CREATE POLICY customers_store_isolation ON retail.customers
    FOR ALL
    TO mcp_user
    USING (store_id = current_setting('app.current_store_id', true));
```

To make our labs 100% runnable in your browser and on **Google Colab Free Tier** with zero Docker setup, our Python `DatabaseProvider` mirrors that exact PostgreSQL RLS policy using an in-memory `sqlite3` tenant-scoped view layer bound to `current_store_id`.
