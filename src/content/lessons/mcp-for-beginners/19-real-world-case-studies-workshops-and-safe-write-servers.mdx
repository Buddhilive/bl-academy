Reading data from an MCP server is forgiving. Taking an irreversible write action, like publishing a post to a company social account or closing a production issue, is not. Across the eight real-world case studies in this unit, the sharpest engineering lessons come from **write-capable remote MCP servers** that must stay safe even when an AI agent hallucinates an ID or retries on a timeout.

## 6 Design Rules for Write-Capable MCP Servers

1. **Open Discovery, Authenticated Execution**: Serve `tools/list` without credentials so registries can inspect schemas, while every `tools/call` requires a valid Bearer token (`401 WWW-Authenticate` otherwise).
2. **Draft-First Workflows**: `create_post` without `scheduledTime` saves a draft; only human-approved `update_post(status="scheduled")` publishes.
3. **Behavioral Annotations**: Set `readOnlyHint=False`, `destructiveHint=True`, and `idempotentHint=True` so Hosts prompt for confirmation.
4. **Un-Inventable Identifiers**: Reject hallucinated connection IDs that were not returned verbatim by `list_connections`.
5. **Actionable Pre-Publish Errors**: Return specific errors (`"Instagram requires media"`) rather than generic `400 Bad Request` codes so the agent can self-correct.
6. **Documented No-Op Test Target**: Accept `platforms: ["playground"]` so CI and reviewers can exercise the full write path without publishing to real accounts.
