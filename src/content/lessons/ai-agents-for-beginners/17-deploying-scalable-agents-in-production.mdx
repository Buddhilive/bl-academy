Up to now, we have built agents that run inside a single notebook. When thousands of users depend on your agent at 3 a.m., the LLM reasoning loop is only **20%** of the system—the other **80%** is the **operational skeleton** wrapped around it: stateless hosting, identity, externalized state, failure handling, cost control, evaluation gates, and observability.

## Prototype vs. Production & Deployment Patterns

| Concern | Prototype | Production |
| :--- | :--- | :--- |
| **Hosting & State** | In-memory notebook | Stateless containers + externalized thread/memory store |
| **Cost & Routing** | Single frontier model for everything | Response cache + complexity router (`gemini-2.5-flash-lite` vs. `gemini-2.5-flash`) |
| **Quality & Trust** | Eyeballing outputs | Automated offline `evaluation_gate(threshold=0.8)` + HITL approval for risky actions |
| **MCP Boundaries** | Unpinned local scripts | Version-pinned MCP servers treated as untrusted boundaries with scoped RBAC |

To scale horizontally without sticky sessions, keep zero per-user state in process memory and pass every request through a **Cache $\rightarrow$ Complexity Router $\rightarrow$ Traced Agent** pipeline:

$$C_{\text{total}} = p_{\text{cache}} \cdot 0 + p_{\text{simple}} \cdot C_{\text{SLM}} + p_{\text{complex}} \cdot C_{\text{LLM}}$$

---

## Release Gates: Offline Evaluation & Post-Deploy Smoke Tests

1. **Offline Evaluation Gate (`evaluation_gate`)**: Runs before deployment; blocks release if pass rate falls below your threshold (e.g., `0.80`).
2. **Post-Deploy Smoke Tests (`lesson-16-smoke-tests.json`)**: A fast, cheap post-deploy check verifying that the live endpoint responds (`HTTP 200`), satisfies `contains_any` / `contains_all` / `contains_none` assertions, and preserves multi-turn thread continuity.
