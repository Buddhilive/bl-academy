You may know that running a single chat session on your laptop is easy, yet serving twenty concurrent users on an edge server quickly stalls if every request pre-allocates a 32K contiguous KV cache. Containerized SLM serving solves this with **PagedAttention** in **vLLM**, declarative **Ollama** containers, and lightweight **ONNX Runtime GenAI** pipelines.

Here is an overview of how these three containerized architectures compare when deploying a 3.8B reasoning model such as `Phi-4-mini-instruct`.

---

## Comparing Three Containerized SLM Runtimes

| Runtime | Core Mechanism | Memory Efficiency | Best Deployment Scenario |
| :--- | :--- | :--- | :--- |
| **vLLM** | PagedAttention + continuous batching | Near-zero internal KV fragmentation (< 4%) | High-throughput multi-user GPU edge servers |
| **Ollama (Docker)** | `llama.cpp` GGUF + REST wrapper | Low idle footprint, single-command pull | Rapid edge prototyping and single-tenant services |
| **ONNX Runtime GenAI** | Compiled ONNX graph + EP abstraction | Minimal C++/Python runtime overhead | Cross-platform CPU, NPU, and embedded Linux/Windows |

---

## How PagedAttention Eliminates KV-Cache Waste

In naive serving, each request reserves a contiguous memory slab for its maximum possible `max_model_len` (for example, 4,096 tokens), even if the prompt and reply only use 350 tokens. Over 60 to 80 percent of GPU VRAM sits idle due to internal fragmentation.

**vLLM** borrows virtual memory paging from operating systems: it divides the KV cache into fixed-size **blocks** (for example, 16 tokens per block) allocated on demand. Memory utilization efficiency improves to:

$$
\eta_{\text{paged}} = \frac{M_{\text{active\_tokens}}}{M_{\text{allocated\_blocks}}}
$$

reducing fragmentation from ~60 percent down to **under 4 percent** and allowing higher batch concurrency on a single T4 or L4 GPU:

```bash
docker run --runtime nvidia --gpus all -p 8000:8000 \
  vllm/vllm-openai:latest \
  --model microsoft/Phi-4-mini-instruct \
  --max-model-len 4096 --gpu-memory-utilization 0.85
```

For production hardening, always run containers with `--read-only`, drop Linux capabilities (`--cap-drop=ALL`), and scrape `/metrics` with Prometheus to alert on `vllm:num_requests_waiting` and `vllm:gpu_cache_usage_perc`.

## Try It Yourself: PagedAttention vs. Contiguous KV-Cache Simulator

Run this Python simulator to compare VRAM utilization when serving 4 concurrent requests of varying lengths under contiguous pre-allocation versus 16-token PagedAttention blocks.

**PagedAttention vs. Contiguous KV-Cache Simulator**

```python
import math

request_lengths = [120, 480, 90, 460]
max_model_len = 4096
block_size = 16

active_tokens = sum(request_lengths)
contiguous_slots = len(request_lengths) * max_model_len
paged_slots = sum(math.ceil(toks / block_size) * block_size for toks in request_lengths)

contig_util = (active_tokens / contiguous_slots) * 100.0
paged_util = (active_tokens / paged_slots) * 100.0
saved_pct = (1.0 - paged_slots / contiguous_slots) * 100.0

print(f"Active Tokens Across 4 Requests: {active_tokens}")
print(f"Contiguous Allocation (max_len={max_model_len}): {contiguous_slots} slots | Utilization: {contig_util:.1f}%")
print(f"PagedAttention (block_size={block_size}):       {paged_slots} slots | Utilization: {paged_util:.1f}%")
print(f"Memory Saved by PagedAttention: {saved_pct:.1f}%")
```

**Expected Output:**

```text
Active Tokens Across 4 Requests: 1150
Contiguous Allocation (max_len=4096): 16384 slots | Utilization: 7.0%
PagedAttention (block_size=16):       1168 slots | Utilization: 98.5%
Memory Saved by PagedAttention: 92.9%
```
